## 约束

| ID | 目标约束 | 失败处置 |
| --- | --- | --- |
| W-01 | 工作项必须关联当前范围版本、目标产物、完成条件和依赖 | 缺项不得进入可执行状态 |
| W-02 | 设计修改必须创建可区分修订，并记录影响项 | 旧审阅不得自动沿用 |
| W-03 | 权威状态写入必须核对预期修订，拒绝过期覆盖 | 冲突返回整合任务 |
| W-04 | 恢复必须核对输入快照、范围、检查点和必要环境 | 不一致项进入待复核 |
| W-05 | 依据变化必须传播到相关设计、覆盖与验收 | 被影响部分转 stale/reopened |
| W-06 | 预算不足、权限缺失和工具失败不得触发静默范围缩减或虚假完成 | 保存一致进度与具体阻塞 |
| W-07 | 多文件更新和导出必须有一致检查点或等价机制 | 崩溃不得暴露混合版本为有效包 |
| W-08 | 已发布套件内容不可静默覆盖；修改产生新版本 | 拒绝原位改写已发布快照 |

## 状态模型

切片使用 `planned / active / blocked / review / closed / reopened`。包使用 `draft / candidate / ready / exported`。公开文档的 `proposed / accepted / superseded` 与这两组运行状态不同，禁止共用一个未定义的 `done`。

切片关闭要求完成条件有依据、相关阻塞问题解决且局部审阅通过；整包发布还要求跨切片整合和交付门通过。来源失效可重开切片，但不改写历史发布结果。

## 检查点最小记录

`checkpoint_id`、`state_format_version`、`scope_revision`、`reference_snapshot_id`、`object_revisions`、`pending_work`、`open_questions`、`content_manifest`。日志顺序不能代替完整检查点，缓存不能替代权威记录。

提交操作以预期修订和完整暂存内容为输入；返回提交后的修订、影响对象和检查点。冲突或不完整写入必须返回明确失败，不允许调用者以缓存成功状态继续发布。

## 测试义务

需要故障注入验证保存中断、恢复旧版本、并行写冲突、来源变化、共享模型变更、预算终止与候选导出失败。具体文件系统和跨平台保证必须实际测试，不把概念上的“原子保存”写成未经验证的现有事实。
