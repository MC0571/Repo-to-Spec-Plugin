# Repo-to-Spec Plugin

[English](./README_EN.md)

> 从已有代码仓库提炼可验证、可追溯、与具体实现解耦的 Canonical Spec。调查者保留来源证据，向实现者交付不包含参考仓库身份、源码或调查记录的规范，使其无需知晓参考仓库的存在，也能独立重建所需能力或将部分能力用于其他系统，并按规范验收所选范围的实现。

## 项目定位

Repo-to-Spec 面向已有代码仓库的逆向规格化，尤其关注需要审慎处理许可和信息边界的使用场景。

它关注的不是“代码是怎么写的”，而是从源码、测试、配置、接口定义和可观察行为中恢复：

- 系统对外提供什么能力；
- 输入、输出和错误如何定义；
- 配置、状态和生命周期如何工作；
- 文件系统、持久化、网络等副作用是什么；
- 顺序、优先级、回退规则、兼容性和安全边界如何约束行为；
- 哪些行为已被证据确认，哪些仍存在歧义或缺口。

调查侧保留证据以便复核；交付给实现者的 Canonical Spec 只包含实现所需的行为与约束。实现者可以重建完整系统，也可以只选取所需能力。若必要的兼容信息会暴露来源，应明确标记这一限制。

## 核心原则

### 以证据为依据

进入 Canonical Spec 的重要要求应尽可能追溯到可复核证据。

调查过程中需要区分：

- 已确认行为；
- 有一致证据支持的推断；
- 尚未确认的假设；
- 未覆盖区域；
- 相互冲突的证据。

无法确认的行为应保持显式不确定，而不是由分析者自行补全。

### 优先关注可观察行为

优先规范外部可观察契约，例如：

- CLI、API 与协议表面；
- 配置和环境变量；
- 输入、输出、错误与退出行为；
- 状态转换与生命周期；
- 文件系统、持久化和网络副作用；
- 顺序、优先级与回退规则；
- 兼容性与安全边界；
- 确定性、幂等性等可观察约束。

### 不依赖具体实现

Canonical Spec 描述“必须成立什么”，而不是“必须怎样实现”。

除非某项实现细节本身属于兼容契约，否则不应把以下内容固化为规范要求：

- 原仓库目录结构；
- 内部类名或函数名；
- 私有数据结构；
- 偶然的模块边界；
- 可替换的算法细节；
- 非必要的技术选型。

交付的规范不应包含参考仓库身份、源码片段或仅用于调查的证据记录。

### 覆盖与闭合

规格完整性不能只由文档长度判断。

调查需要持续识别：

- 已覆盖的行为面；
- 尚未调查的区域；
- 未解决的歧义；
- 相互矛盾的证据；
- 独立实现仍然缺失的信息。

只有在关键行为和约束达到足够闭合后，规范才能作为可靠的实现契约。

### 规范具有约束力

Canonical Spec 是行为与约束的规范性来源。

实现可以采用不同的内部设计，只要最终可观察行为满足同一份规范。

## 工作模型

```text
参考仓库
        ↓
仓库调查
        ↓
证据与覆盖范围（调查侧）
        ↓
Canonical Spec
        ↓
规范验证
        ↓
交付给实现者
        ↓
重建或选择性采用
        ↓
符合性证据
```

其中：

- **仓库调查**：定位和验证与行为相关的源码、测试、配置和运行证据；
- **证据与覆盖范围**：在调查侧记录证据来源、置信度、覆盖范围和未决项；
- **Canonical Spec**：整理实现无关的行为、接口、约束和边界；
- **规范验证**：检查完整性、明确性、一致性、可验证性和实现独立性；
- **交付给实现者**：只提供通过验证的规范，不提供参考仓库或调查记录；
- **重建或选择性采用**：按完整规范或选定的能力范围开展独立实现；
- **符合性证据**：为所选范围的实现验收提供可复核依据。

## 边界

Repo-to-Spec 不以以下事项为目标：

- 复制参考仓库的内部架构；
- 把代码结构直接改写成文档；
- 为独立实现预先指定目录、模块或算法；
- 用未经验证的假设填补规格空白；
- 把实现计划或任务分解当作 Canonical Spec 的一部分。

本项目不判断特定仓库的许可条款是否允许某项使用，也不保证规范或实现自动获得使用授权。
