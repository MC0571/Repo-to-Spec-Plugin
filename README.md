# Repo-to-Spec Plugin

[English](./README_EN.md)

> 将成熟软件仓库转化为一套高度忠于目标产品、尽可能完整准确、但不绑定原实现方式的系统规格套件，使新的团队或编程智能体可以独立实现完整产品，或有选择地吸收其中的能力、工作流、模块与子系统。

## 为什么存在

成熟的软件仓库不仅包含代码，也沉淀了已经被真实开发和使用验证过的产品判断、交互规则、系统边界、异常处理和工程取舍。重新开发类似产品时，如果忽略这些经验，团队往往会重复造轮子，也会重新踩一遍前人已经踩过的坑。

但“开源”并不意味着所有仓库都适合作为新项目的直接实现基础。不同许可证、附加条款和使用政策可能带来不同限制。Repo-to-Spec 借鉴净室设计的思想，将值得借鉴的产品与工程知识同原仓库的具体实现分离：理解成熟项目已经解决了什么，再把这些成果重新表达为可独立实施的规格。

更完整的项目动机、目标状态和取舍原则见 [VISION.md](./VISION.md)。

## 能为你做什么

Repo-to-Spec 面向希望借鉴成熟软件成果、但不直接继承其实现的团队和编程智能体。

- **独立实现完整产品**：将目标产品的功能、体验、外部契约和关键系统设计恢复为可直接用于开发的规格。
- **选择性吸收成熟能力**：只选择某个能力、工作流、模块或子系统，将其作为现有产品继续设计和集成的输入。
- **为编程智能体提供开发输入**：实现方无需知道参考仓库存在，也不需要在编码过程中重新完成仓库研究、需求恢复和关键设计。

Repo-to-Spec 交付的不是可复制的代码，而是**可独立实施、可组合、可继续设计的完整规格**。

## 交付物

最终交付是自包含的 `SYSTEM_SPEC/` 系统规格套件，而不是一篇仓库说明或按源码目录组织的 Wiki。

套件按目标产品的实际需要组合多种规格资产，例如：

| 设计内容 | 典型载体 |
| --- | --- |
| 产品目标、能力、业务规则与完整流程 | 人类可读规范 |
| 页面、交互、视觉、状态与无障碍要求 | 体验规范、设计令牌、必要的视觉资产 |
| 领域、状态、职责、并发、恢复和安全设计 | 结构化模型与技术规范 |
| API、事件、配置与文件格式 | 接口定义、协议契约、Schema |
| 边界条件与验收行为 | 场景、样例数据、测试向量及适用的符合性资产 |
| 可变与不可变的实现选择 | 实现自由与约束说明 |

具体目录和文件格式不要求所有项目完全一致。判断完整性的标准是：在声明的目标范围内，新的实现团队是否已经拥有足够的产品、体验和技术设计，可以直接进入工程实现，而不必重新补做关键决策。

## 核心原则

### 高度忠于目标产品

规格应尽可能准确恢复目标产品的功能、体验、接口、状态语义和必要系统约束。正常路径、异常路径、边界状态和功能组合都属于产品的一部分，不能用“主要功能摘要”代替完整设计。

### 设计完备，实现解耦

关键产品与系统设计必须明确，但不应无必要地固定原仓库的目录、内部符号、框架、私有数据结构或偶然模块边界。不同团队可以选择不同技术实现，只要满足同一套规范结果和约束。

### 最终套件必须自包含

实现团队只接收系统规格套件，不需要访问参考仓库，也不应被要求根据源码补齐未说明的行为。调查中的未决问题可以存在，但影响实施的重要问题不能被包装成最终交付。

### 工具服务于交付，而不是定义产品

文件搜索、测试、运行观察以及 GitNexus、CodeStory、Serena、OpenDesign 等外部能力都只是可选手段。插件必须围绕最终规格质量组织工作，而不是要求用户先搭建某组特定工具链。

### 效率体现为少做一遍前置工作

目标不是生成更多调查记录，而是让新团队少做一遍仓库理解、需求恢复、体验梳理和关键系统设计。内部记录、来源回查和验证机制只在它们有助于提高交付质量或减少返工时发挥作用。

## 工作方式

```text
成熟软件仓库与可用产品上下文
              ↓
        Repo-to-Spec
              ↓
    完整的系统规格套件
              ↓
不了解参考仓库的独立团队或编程智能体
              ↓
不同内部实现，满足同一套产品与系统规范
```

插件会围绕最终交付持续理解目标产品、补齐影响实施的设计缺口，并将结果组织为人类和工程工具都可以消费的规格资产。具体调查、编排和工具选择属于实现手段，不构成下游团队的依赖。

## 项目边界

Repo-to-Spec 不是：

- 仓库 Wiki 或源码摘要生成器；
- 把目录、类、函数和调用关系直接翻译成规格的工具；
- 通过复制内部架构来替代独立设计的代码复刻器；
- 以证据记录数量、工具集成数量或文档篇幅衡量价值的研究平台。

本项目也不判断特定仓库的许可证、附加条款或其他政策是否允许某项具体使用，不提供法律意见，也不保证生成规格或后续实现自动取得任何授权。使用者仍需自行确认适用的许可、合同和合规要求。

## 当前状态

项目正在从目标状态反推插件、技能和运行能力的设计。仓库已有基础 CI 和设计登记表检查；尚未提供可安装插件、正式生成命令或经过产品级验证的系统规格生成能力。

README 描述稳定的产品定位；[VISION.md](./VISION.md) 描述目标状态；[M0 设计基线](./docs/reviews/M0-ADOPTION.md)已在限定范围内采纳，不代表产品能力实现或全部详细设计获批。源快照见 [当前状态](./docs/CURRENT-STATE.md)，目标能力进展见 [能力地图](./docs/planning/CAPABILITY-MAP.md)。
