# 产品交付模型

> 基线：DB-20260928 · 状态：待评审提案 · 类型：目标设计
> 本文承接现有愿景，不表示能力已经实现；变更与采纳规则见文档入口。


## 1. 消费者与交付方式

沿用现有愿景的三类使用者：独立重建团队、希望选择性吸收成熟能力的团队、只消费规格的编程智能体。前两类是不同范围模式，不是不同质量档次；第三类强调可导航、无隐含上下文和结构化契约。

| 场景 | 输入与决策 | 必须产出 | 不能被称为完成的情况 |
| --- | --- | --- | --- |
| 完整产品独立实现 | 目标版本、完整范围、支持环境及必要材料 | 所有声明能力及其交互、体验、共享规则和必要技术设计 | 只有主要功能或架构概要 |
| 选择性吸收 | 被选能力、目标产品约束、允许的适配 | 所选能力与传递依赖、边界协作契约、允许改动 | 直接裁掉被选能力依赖的权限、数据或生命周期 |
| 规格更新 | 原套件版本、参考版本或范围变更 | 变更内容、影响项、重新验证结果及新包版本 | 全量重写却不能解释变化，或仍使用已失效依据 |
| 中断后恢复 | 最近一致检查点、原范围、有效输入 | 可恢复的下一项交付和有效既有成果 | 根据聊天摘要盲目认定旧结论仍有效 |

## 2. 交付单位不是源码目录

`DeliverySlice` 是围绕一个可说明、可审阅的产品能力或工作流划定的工作单位。可以跨多个仓库目录，也可以只覆盖一个大模块中的部分产品行为。切片完成需要同时说明：参与者和目标、入口、正常与异常路径、状态与副作用、体验、数据与协作、验收以及共享依赖。

例如“取消进行中的导入”是一个交付切片；`src/import/` 不是天然的产品边界。该切片需要回答请求何时可取消、重复取消、已写数据如何处理、界面如何反馈、刷新或重连后的状态、权限及最终一致性，不应只列一个 cancel 函数。

此例是设计方法示例，不声称任何特定参考仓库具有这些行为；实际结论必须由可用材料、被确认的设计依据或用户决定支持。

## 3. 完整交付矩阵

| 交付维度 | 必须回答的设计问题 | 适用条件 |
| --- | --- | --- |
| 产品 | 目标、参与者、权限、能力边界、配置、默认值、规则组合 | 所有范围 |
| 工作流 | 前置条件、触发、结果、失败、中断、重试、恢复、终态 | 存在操作或生命周期 |
| 体验 | 信息架构、导航、视图、组件、状态、反馈、视觉与交互、键盘与焦点 | 对人类呈现界面、命令输出或文档化交互 |
| 数据 | 语义、身份、所有权、验证、生命周期、持久化与迁移 | 存在输入、输出或状态 |
| 接口 | CLI/API/事件/协议/配置/文件格式、错误与兼容 | 存在外部或必要协作界面 |
| 逻辑技术设计 | 职责边界、协作、事务、并发、幂等、失败传播、安全 | 实现目标行为所必需 |
| 运行约束 | 部署与环境、资源、性能、可靠性、可观测性、升级与恢复 | 根据目标支持环境与产品约束确定 |
| 实施边界 | 必须相同的结果、允许变化的机制、允许范围 | 所有范围 |
| 验收 | 可观察结果、容差、测试向量、状态与错误断言 | 每项规范性设计 |

不适用必须写依据。没有 UI 的库无需虚构页面；有 UI 的产品不能用“已提取令牌”代替完整交互。原项目没有可验证性能目标时，不得把经验数值当成恢复事实；必要的新约束需明确决策来源。

## 4. 恢复、设计与改动的分界

**恢复事实**描述目标产品已经存在的规则，内部依据可来自源码、测试、运行、文档或已确认的产品上下文。材料矛盾时标为待核实，不能简单宣布源码永远优先于产品要求。

**独立设计决策**为满足已确认规则而给出逻辑职责、数据所有权与协作方案。可以不同于原仓库内部架构；需要说明所满足的要求、被排除的方案与不改变的行为，不能伪称“源码就是这样”。普通内部设计无需逐条询问用户，但涉及产品承诺变化时必须提升为用户取舍。

**授权产品改动**例如改变默认值、移除某能力或采用新交互，需要用户明确同意并更新范围或产品约束。它不能混入“忠实恢复”，也不能借“选择性吸收”自动获得改动权限。

## 5. 选择性吸收的依赖闭合

从用户所选能力开始，沿数据、身份与权限、配置、事件、状态、错误恢复、共享视觉和生命周期查找依赖。每条依赖只能采用三类可见处置：纳入交付范围；以完整边界契约交给目标环境；经用户批准改造或排除。

结果必须形成依赖闭合清单，说明谁提供什么、失败时怎样、如何验证。与原产品相关但不再需要的能力可以排除；被排除原因是目标边界，而不是调查困难。依赖环需整体处理，不能在每个切片里相互写“由另一模块负责”而无人承担。

## 6. 交付成功与非目标

一次最终交付要使接收者能够开始自己的工程实现，而不必补做关键产品、体验和逻辑系统设计。套件必须指明支持版本、范围与环境；没有重要阻塞问题；有内部和外部一致的验收语义；没有要求访问参考代码的隐含输入。

不是本产品强制交付的内容：新实现源码、统一技术栈、工程排期、按源码文件拆解的任务列表、全量参考仓库索引、每次运行的完整重建项目。它们可以作为下游工作或特定验证手段，但不覆盖或替代设计交付。
