# 独立消费与符合性评测

> 基线：DB-20260928 · 状态：已采纳 · 类型：目标设计
> 本文承接现有愿景，不表示能力已经实现；变更与采纳规则见文档入口。


## 1. 两个不同的闭环

**交付闭环**是每次任务必需：明确范围 → 完成产品/体验/逻辑技术设计 → 结构与语义检查 → 隔离消费检查 → 冻结套件。它不要求先实现一个新产品。

**产品效果闭环**用于验证 Repo-to-Spec 是否真正创造价值：选择代表性参考产品 → 生成套件 → 隔离的实现团队仅凭套件开发 → 按声明约束评测 → 归因并改进。它可以按版本、重要能力变更或高风险场景执行，不强制每次交付完整重建。

这一区分保持现有 `VISION.md` §6、§9 的产品边界，而不减弱最终可独立实施的目标。

## 2. 独立消费检查

接收者在不含参考源码、原调查会话和内部工具缓存的环境只读取 `SYSTEM_SPEC/`。检查能否解释完整工作流、找到状态与错误语义、确定数据及接口、了解视觉与交互要求、明确逻辑职责和实现自由，并说明验收方法。

发现必须向原调查者询问的关键产品或系统决策时，记录为套件缺口；工程上已经明确允许的技术选择不算缺口。问答测试和实现者走查要覆盖失败、权限、取消、恢复及组合行为，不能只读首页。

这种检查证明的是消费准备度，不是运行符合性。仅切换同一 Agent 的角色名称而保留原上下文，不可标记为隔离消费。

## 3. 结果评测设置

评测者可掌握参考环境与内部依据；实现者只拿公开包；两者上下文和存储分离。记录目标版本、范围、平台、环境、工具和模型版本、允许差异及评价资产。环境无法等价时不得把所有输出差异归于规格缺陷。

评测目标以公开规格为主。参考系统行为用来发现规格恢复错误，不自动压过已批准的产品改动或明确实现自由。原实现的缺陷是否需要保持，是范围与兼容决策，不是默认规则。

## 4. 评价维度

| 维度 | 检查内容 | 允许变化的条件 |
| --- | --- | --- |
| 产品与流程 | 能力、规则、权限、默认、组合和异常 | 公开规格批准的产品差异 |
| 体验 | 布局、状态、反馈、导航、输入与无障碍 | 规格定义的容差、响应范围和平台差异 |
| 数据与接口 | 格式、状态、错误、兼容、副作用 | 不改变对外语义的内部表示 |
| 逻辑技术约束 | 所有权、一致性、并发、恢复与安全 | 满足相同约束的内部机制 |
| 运行 | 适用部署、资源、性能和可靠性 | 在声明条件和容差内 |
| 交接成本 | 关键澄清、补做设计、返工、来源回查 | 不将合法实现选择误计为缺失 |

概率输出、并发与时间行为使用允许结果集合、关系或区间；不能强求不适用的逐字一致。容差来自被确认的产品要求或显式设计，不凭经验杜撰为参考事实。

## 5. 问题归因

`spec_gap`：缺失或不清楚的设计；`recovery_error`：恢复事实错误；`design_conflict`：独立设计不能满足已定约束；`implementation_gap`：实现未满足充分明确的规格；`evaluation_gap`：测试或比较方式错误；`environment_gap`：环境差异；`reference_ambiguity`：参考材料冲突；`allowed_variation`：已声明自由，不是缺陷。

每项问题记录证据、受影响规范和复现条件；允许待归因，不强制立刻二选一。修正规格需要重跑受影响验收；实现问题由下游处理；评价错误不能通过改产品规格掩盖。

## 6. 防止循环自证

不能仅让同一生成步骤写规格、写测试，再用自己写的测试宣称完备。至少引入独立消费、保留的测试情景、参考环境观察或不同实现者中的适用组合。测试样例不能只覆盖生成时已列出的成功路径。

跨内部实现的复现是验证实现解耦的有力实验，但有限实验不是普遍等价证明。报告必须说明实际检验了哪些范围、条件和质量维度。

## 7. 与建设路径的关系

从 M0 开始设计盲消费与失败案例；从首批切片开始做小范围消费检查；在目标能力完整后开展代表性重建评测。验收思路不推迟到项目末期，完整重建也不劫持每一次交付。

详细场景、指标与回归策略见 [验证策略](../planning/VALIDATION-STRATEGY.md)。
