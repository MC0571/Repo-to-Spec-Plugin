# 系统规格套件模型

> 基线：DB-20260928 · 状态：已采纳 · 类型：目标设计
> 本文承接现有愿景，不表示能力已经实现；变更与采纳规则见文档入口。


## 1. 规范对象与物理载体分离

`SYSTEM_SPEC/` 沿用当前仓库的概念性根目录。目标是稳定**内容语义、引用与消费方式**，不是让每个目标产品生成相同文件树。本文提出套件模型；尚未发布稳定 Schema、CLI 或兼容承诺。

规格组织器承担两类不同工作：语义设计与撰写可能依赖模型；文件组装、标识检查、路径隔离、内容摘要和格式校验应尽可能确定性。不得用“编译”一词暗示自动证明设计完备。

## 2. 必需与条件性内容

| 语义角色 | 要求 | 最小内容 |
| --- | --- | --- |
| 阅读入口与清单 | 必需 | 范围、版本、阅读路径、文件角色、规范性和引用规则 |
| 产品与能力 | 必需 | 目标、参与者、能力、规则、边界与依赖 |
| 领域与术语 | 必需 | 一致术语、数据含义、身份与状态；复杂度按产品而定 |
| 工作流与体验 | 必需说明适用性 | 正常和异常路径、可观察反馈；有 UI 时含完整视觉与交互规则 |
| 接口与格式 | 按已发现表面必需 | CLI/API/事件/配置/文件/协议的输入输出、错误、默认与兼容 |
| 逻辑技术设计 | 按实现必要性必需 | 职责、所有权、协作、事务、并发、恢复、安全和运行约束 |
| 实现自由与约束 | 必需 | 哪些可变、允许边界、不能改变的结果以及验收 |
| 验收 | 必需 | 与设计元素关联的场景、样例、断言、容差及必要可执行资产 |
| 必要资产与说明 | 按产品需要 | 令牌、示意、数据样本、合法必要资源和使用条件 |

“不适用”是一项有理由的判断。缺失格式、没有权限观察界面或运行失败不等于不适用。不同产品可以选不同载体，但不能漏掉相同的语义义务。

## 3. 公开清单的候选字段

推荐以机器可读清单承载 `package_id`、`package_version`、`format_version`、`status`、`scope`、`entrypoint`、`artifacts`、`requirements`、`acceptance_assets`、`implementation_freedoms` 和 `dependencies`。

每个产物给出包内相对路径、媒体或格式类型、语义角色、规范性、内容摘要及所承载的元素 ID。每条引用必须指向包内存在元素，或明确声明的外部标准/运行依赖；不能通过源码 URL 补足关键语义。

本字段表是设计提案，不是已经受支持的 JSON API。M1 建立具体可序列化 Schema 候选，按 [OD03](../decisions/OPEN-DECISIONS.md) 在 M4 前评审接受；承诺兼容前应以 CLI、UI 和跨能力实例共同验证，而不是凭一个模板冻结。

## 4. 规范元素的表达

一项可实施的规则至少应让接收者确定：适用对象与条件、输入、前置状态、动作、成功结果、失败与副作用、时间或并发约束（适用时）、允许差异和验收方式。

自然语言内容可以与结构化契约共同承载同一元素。必须明确哪个载体对哪个字段具有规范权威；文档与 Schema 冲突不能让接收者自行选择。示例默认是非穷举说明，除非明确被声明为规范性测试向量；例子不能覆盖掉正式边界规则。

## 5. 体验与技术的联动

例如取消行为必须让产品规则、按钮可用状态、视觉反馈、后端任务状态、持久化结果和重连体验描述同一件事。页面稿不单独决定产品语义；接口返回码不单独决定用户反馈。状态与关键术语通过元素 ID 交叉引用。

逻辑技术设计应足够使这些行为落地，但不指定无必要的原类名和模块路径。必要的协议、数据约束或平台兼容要求即便带技术名称，也不应被当作“实现耦合”删除。

## 6. 实现自由是正面授权

自由项需要写明：选择维度、允许选项或边界、必须保持的行为与约束、验证方式。不能只写“数据库自行决定”而漏掉一致性、事务或恢复要求。无法确定的关键结果是未决问题，不是自由项。

新团队可基于完整规格再作产品改动；改动后相应要求和验收随之更新。原套件不强制团队永远保持原产品组合，但不能把未授权偏差声称为忠实符合。

## 7. 组装、检查与冻结

设计元素归类 → 选择载体 → 生成草案资产 → 对齐术语与引用 → 检查格式和语义 → 生成公开投影 → 隔离消费检查 → 冻结清单与版本。

导出采用显式产物允许清单。源路径、内部符号映射、调查日志和工具调用记录不进入实施套件。公开的“要求 → 验收”关系可以保留；内部的“源码 → 设计”关系留在工作区。

草案和候选必须显式标识，不能以文件已生成或哈希已计算作为最终交付判断。阻塞问题未解决时，可交付进度材料但不可标记完整套件。详细交付门见 [质量契约](../../contracts/quality-gates.md)。

## 8. 版本与扩展

套件内容版本、格式版本和参考输入版本是三个不同概念；参考版本只需内部可回溯，公开表达目标产品版本及范围。格式版本决定消费者怎样读取；内容版本决定规范变化。

增加一种产物格式时，必须定义适用性、规范权威、验证器、内部/公开边界和旧消费者的失败语义。尚不能理解的规范性格式不能默默忽略。最终格式变更走公开契约评审，不由某个 Provider 的输出格式决定。
