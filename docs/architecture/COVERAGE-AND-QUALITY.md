# 覆盖、完整性与质量判断

> 基线：DB-20260928 · 状态：待评审提案 · 类型：目标设计
> 本文承接现有愿景，不表示能力已经实现；变更与采纳规则见文档入口。


## 1. 覆盖是反馈，不是证明全部已知

覆盖模型用于回答声明范围内哪些交付义务已经满足、哪些仍缺少，以及下一步做什么。它不是代码覆盖率，也不能把已列清单的完成比例当作所有未知行为的完备性证明。

需要同时看三个问题：产品面是否发现充分；必要设计是否已经表达；表达出来的设计是否正确、自洽、可实施。只做第三项格式检查不能补足前两项。

## 2. 覆盖义务与适用性

按“产品能力/工作流 × 产品/体验/技术维度 × 支持环境与重要状态”建立义务。维度包括正常、异常、空状态、权限、默认、配置组合、持久化、并发、中断、恢复、升级和必要外部依赖。按产品实际选择，不盲目生成笛卡尔积。

义务状态为 `unknown / applicable / not_applicable`；适用项进度为 `missing / drafted / reviewed / closed / stale`。不适用需理由与审阅；`unknown` 不能计入已闭合。覆盖义务关联设计元素和验收，阅读过相关源码不构成闭合。

产品面发现的输入至少交叉检查多个适用视角：用户入口和帮助、公开接口、配置、测试、运行界面、数据迁移、依赖和历史。并非每个任务都必须使用所有视角，但未用视角及其影响必须可解释。

## 3. 四层质量检查

| 层 | 可以检查什么 | 不能声称证明什么 |
| --- | --- | --- |
| 结构检查 | 字段、类型、引用、路径、状态合法、产物存在 | 规则是否忠实、体验是否完整 |
| 语义审阅 | 规则一致、边界明确、技术设计可落地、实现自由有边界 | 未见材料中的行为必然不存在 |
| 隔离消费检查 | 无参考资料的接收者能否找到实施所需设计 | 已经实际实现并满足所有运行目标 |
| 产品结果评测 | 在指定场景与环境下的新实现符合性及交接成本 | 对任意实现、环境和未来版本的普遍保证 |

自动化与语义审阅必须分别报告。关键词规则可提示“合理”“参考实现”等风险表达，但不能可靠判断所有实现耦合、隐藏依赖或设计充分性。

## 4. 阻塞问题分类

阻塞最终交付：缺失关键产品结果；重要状态或边界未定义；相互冲突的规范；必要接口/数据/体验缺失；未批准范围缩减；原仓库回查依赖；无法落实的技术设计；必要授权或资产问题未解决。

可不阻塞交付但需处理：不会改变任何规范结果的排版瑕疵、明确处于范围外的建议、非规范性说明优化。严重性由影响判断，而非问题数量或工具给出的分数。

## 5. 完成判断

对最终套件要求：范围与适用性清楚；范围内重要义务均有设计和审阅依据；阻塞问题为零；跨文件规则无已知冲突；公开引用和必要资产可用；隔离交接检查通过；没有把未完成设计转给实施方。

“阻塞问题为零”是发布条件，不代表没有任何未知风险。交付报告应说明检查范围、环境和方法，以及不能外推的边界，不能用免责声明为已知缺失辩护。

范围发现不足或缺少关键运行条件时，即使清单 100% 勾选，也不能宣称最终交付。比例指标只辅助定位进度；不设一个统一 95% 分数替代交接门。

## 6. 反馈到执行

每个失败结果至少包含：受影响的产品能力/设计元素、具体缺口、阻塞性、已有材料和建议动作。编排将其映射回调查、独立设计、范围决策、格式修复或验收修订，而不是全部归为“再多读代码”。

来源变化使义务变为 `stale`；修订通过后重新关闭。一个切片闭合后仍可能被跨能力冲突重开。

## 7. 评测与演进

检验产品效果应优先观察关键澄清需求、来源回查次数、补做设计的工作量、符合性问题与整体返工，而非文档长度。成本、耗时和模型调用量与质量一起测，不以低成本掩盖交接失败。

评测集与验收方法见 [验证策略](../planning/VALIDATION-STRATEGY.md)；一次交付的门禁与版本行为见 [质量契约](../../contracts/quality-gates.md)。
