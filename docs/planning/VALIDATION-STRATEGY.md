# 验证与回归策略

> 基线：DB-20260928 · 状态：待评审提案 · 类型：验证规划
> 本文承接现有愿景，不表示能力已经实现；变更与采纳规则见文档入口。


## 1. 先区分本包检查与产品验证

本设计包新增的 `scripts/check_design.py` 使用 Python 标准库，检查文档本地链接、登记表身份和引用、依赖环、合同 ID、能力与里程碑关系，以及状态提升是否带有证据引用。其 `--self-test` 检查若干已知无效登记和路径场景会被拒绝。

它**不生成规格、不验证目标产品行为、不判断自然语言是否充分、不执行完整独立实现评测**。证据路径存在也不能证明其中内容真实；语义与采纳仍需评审。所有 Axx 产品验收目前均为 `not_run`，所有 B-xxx 评测集均为 `planned`。

```bash
python3 scripts/ci_check.py --self-test
python3 scripts/check_design.py --self-test
python3 scripts/check_design.py
python3 scripts/ci_check.py
```

最后一条依赖 Git 工作树，并只覆盖受 Git 跟踪的 Markdown；新增文件需纳入暂存区再检查。设计检查器会直接检查包内文档，不要求 Git，因此也可以在解压后的 `repository/` 执行。现有 CI 的 `required` 检查被保留，增加设计检查和自检，不新增产品运行技术栈。

## 2. 产品评测集的目标组成

下表是需要建设的测试材料，不是现成测试已通过的清单。选择真实参考项目时记录合法可用条件、固定版本和支持环境；不因为仓库知名或工具易接入而替代目标代表性。

| 集合 | 目标类型 | 必须检验的要点 |
| --- | --- | --- |
| B-CLI | CLI、配置与文件副作用 | 帮助、配置优先级、退出码、stdout/stderr、错误、原子写入与重复执行 |
| B-WEB | 完整 UI 与交互 | 正常、空、加载、错误、部分成功、键盘/焦点、响应式及动态反馈 |
| B-SERVICE | 状态化服务与逻辑技术设计 | 接口、事件、数据所有权、事务、并发、取消、恢复和部署约束 |
| B-MIXED | 跨入口混合产品 | 多个入口、共享规则、不同进程与体验状态；防止按目录替代产品边界 |
| B-SELECTIVE | 选择性吸收 | 权限、配置、持久状态等传递依赖；边界契约、依赖环与范围变更 |
| B-BLOCKED | 输入缺失与覆盖误判 | 无法运行、缺外部状态、清单漏项、unknown 被错误计为完成 |
| B-CONFLICT | 事实与设计冲突 | 文档/测试/源码冲突、结构通过但语义缺失、独立设计不满足规则 |
| B-RECOVERY | 持久化与崩溃恢复 | 保存中断、并发过期写入、半包导出、损坏检查点 |
| B-ISOLATION | 来源与安全边界 | 指令注入、资料外发、路径穿越、越界符号链接、内部内容泄漏 |
| B-NATIVE | 原生与增强对照 | 禁用可选工具、未注册、超时、结果截断和过期索引 |
| B-HOST | 真实宿主与包格式 | 声明标准、客户端版本、加载、取消、恢复和适配差异 |
| B-DELTA | 增量变更 | 共享配置、权限、状态、视觉与接口变化的影响传播 |
| B-REBUILD | 独立实现与保留场景 | 隔离接收者、不同内部方案、未暴露的评价场景和差异归因 |
| B-REGRESSION | 失败回归 | 最小复现、合同或技能修订、正反例与适用范围 |
| B-COST | 整体工作量与效率 | 包含研究、设计、生成、审阅、澄清与返工的成本对照 |

合成样例用于可控失败与边界；真实项目用于复杂度和交接效果。两者都需要，前者不能证明实际产品广度，后者不能稳定覆盖所有难复现故障。不同集合可以复用同一固定项目，但必须说明覆盖关系。

## 3. 各层自动化

结构层：包结构、Schema、元素和引用、路径、状态机合法性、数据类型、必要字段、版本迁移、导出允许清单。相应实现出现时必须有自动化正反例。

语义层：产品规则完整、体验可执行、逻辑设计足够、独立性、材料冲突和共享约束。采用固定任务、评分说明、反例和受控审阅，不能只用关键词或同一模型自评。

交接层：独立接收者只读实施包，回答保留问题并规划或完成约定任务，记录必须补问的关键设计与回查需求。

结果层：代表性独立实现与参考观察或规范验收对比，分类恢复、设计、实现、环境、评价和允许差异。它是产品评测，不是每次任务都必须额外构建新系统。

## 4. 验收记录

Axx 的具体方法与通过条件在 [设计登记表](design-baseline.json)。执行记录至少包括：输入与范围版本、工具/模型/宿主、允许操作、检查版本、实际结果、反例、失败归因、证据位置、日期和限制。

检查结果只能写 `not_run / partial / passed / failed`。没有执行环境写 not_run；部分范围通过写 partial。不能因为测试工具不存在而用“人工看过”代替未执行的运行符合性检查。

## 5. 关键指标及解释

交付质量优先观察：范围内重要未决数、关键设计补做项、无来源环境的消费成功、必须回查参考资料的次数、行为与体验符合性、共享规则冲突。发布门不接受已知的重要设计缺失。

效率同时统计：从接入到可用交接的总历时、使用者介入、模型与工具成本、下游澄清和返工。不能仅报告首份 Markdown 的生成时间或 token 数。

尚未取得基线前不虚构统一质量分数或成本百分比目标。对照实验先固定范围、环境和评价方法，再比较人工/通用 Agent 流程与本产品流程。报告样本、波动与适用范围，不能从单次好结果外推全部产品。

## 6. 避免泄漏与循环自证

评价场景中保留不对生成者公开的任务与边界问题；隔离实施者与研究上下文。参考观察用于核实恢复，不直接进入实施方材料。设计中的授权差异与实现自由必须纳入评价，不能把允许变化算失败。

模型生成规范与同模型生成测试可能共享错误。至少使用适用的独立消费、保留场景、参考运行或不同实现者进行交叉验证；不得把“自己的测试全部通过”作为充分性证明。

## 7. 回归工作流

发现实际交接或运行失败 → 最小化输入与复现 → 判定问题属于材料、恢复、设计、导出、实现还是评价 → 修改权威合同/技能/检查器 → 加入合适层级的正反例 → 复测 → 明确受保护范围。

只有已知问题被相应案例稳定保护，才能提升 `regression_status`；不把一个空测试目录算作保护。经验可转为脱敏规则或测试，但不自动把用户源码、日志和私有设计上传公共仓库。
