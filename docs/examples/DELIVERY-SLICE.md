# 交付切片走查示例

> 基线：DB-20260928 · 状态：待评审提案 · 类型：设计示例
> 本文承接现有愿景，不表示能力已经实现；变更与采纳规则见文档入口。


## 1. 示例来源与用途

本例是为检验设计方法构造的**虚构用户需求**，不是对真实仓库的调研结论，也不是一个完成的 Repo-to-Spec 产品。它展示怎样同时闭合功能、体验和技术，而不是把产品范围缩成 MVP。

用户已确认：导入任务可在运行中取消；取消后不发布半成品；取消请求重复发送不得产生新的副作用；任务已完成时取消不能撤销结果；断线重连后可查询最终状态。以下由这份需求明确给出的内容视为示例输入事实，其余逻辑安排标为独立设计。

## 2. 产品与状态规则

状态为待开始、运行中、取消处理中、已取消、已完成、失败。取消请求仅对运行中任务发起状态转换；重复请求返回当前取消状态；完成提交与取消确认存在竞争时，只能进入一个终态，必须保持“无半成品发布”。

上述竞争处理需要进一步设计，不能直接写“按原实现处理”。本例推荐以任务的单一状态所有者协调终态提交：先取得完成提交权则保持已完成；先取得取消权则禁止发布结果。它是满足用户规则的逻辑设计，不指定数据库、锁类型或原模块。

## 3. 体验说明

运行中显示取消入口；请求处理中显示明确进度并防止重复触发，但断线或重复请求的后端语义仍需幂等。已取消显示任务结果未发布；已完成不能显示取消成功。重新进入页面按任务持久状态恢复反馈，不依赖浏览器内存。

视觉尺寸、颜色、文案、键盘焦点和无障碍详细值在本示例输入中未给定，因此本例仍是**走查材料而非可发布体验规格**。真实任务必须调查或完成经约束的设计，不得以“按钮合理摆放”等表述宣称完成。

## 4. 数据与协作

任务拥有状态、结果发布标记和终态修订；进度展示读取任务状态，不能另建一个互相矛盾的 UI 终态。执行工作者可产生暂存数据，但结果发布必须通过任务所有者的终态判断；取消后的暂存清理策略需要定义是否同步完成及失败恢复。

本例尚未定义数据保留期限与清理失败的用户可见规则，必须保留具体未决问题。它们不能被自动归类为“实现自由”。

## 5. 验收与边界

可立即形成的验收：重复取消无额外副作用；终态唯一；取消后不发布半成品；任务完成后取消不撤销结果；重连展示持久状态。仍需补全取消与完成竞争的可观察响应、清理失败规则和完整体验数值，才能关闭切片。

可明确开放的实现选择：使用线程、协程或队列；使用哪种存储技术。它们必须保持终态唯一、无半成品发布和恢复语义，不能改变产品结果。
