# SYSTEM_SPEC/ 输出标准

本文件供撰写与整理正式套件时读取。`SYSTEM_SPEC/` 是概念性根目录；可以是一份主规范加少量契约，也可以按需要拆为多个文件。选载体以能被实施和验证为准，不创建空目录凑齐格式。

## 阅读入口

入口说明目标产品/能力、声明范围、支持环境与版本、明确排除项、文件顺序、术语、规范性权威、外部依赖和验收入口。选择性吸收时列出必要依赖的处理方式。不要把参考仓库路径、内部调查笔记或原实现符号当实施前提。

## 按适用性写全的内容

| 设计面 | 实施者需要知道的内容 |
| --- | --- |
| 产品和参与者 | 用户目标、角色、权限、能力边界、默认值、共享规则和能力组合。 |
| 工作流 | 前置条件、触发、顺序、正常结果、边界、失败、中断、重试、恢复、终态与副作用。 |
| 体验 | 信息架构、入口、导航、每个关键视图和状态、文案/反馈、键盘与焦点、可访问性、响应和视觉约束；无图形 UI 则写实际的人机交互。 |
| 数据与状态 | 概念、身份、字段含义、验证、不变量、所有权、生命周期、持久化/删除、迁移或兼容。 |
| 接口与配置 | 实际对外的 CLI/API/事件/协议/文件格式、输入输出、默认、错误、权限、版本与兼容语义。 |
| 必要逻辑技术设计 | 职责、协作、事务或原子性、并发与幂等、失败传播、安全边界、运行条件、性能与可靠性约束；只写影响结果的约束。 |
| 验收 | 对每条重要规则给出可观察的场景、输入/前置状态、操作、结果和错误断言；适用时给样例或测试向量。 |

不是每类产品都需要同样篇幅。`不适用`须有产品原因；“没看到材料”“工具不可用”是未知或验证限制。对有 UI 的产品，接口列表无法代替交互与视觉状态；对无 UI 的库，不虚构页面。

## 可填写的设计字段

字段是检查设计是否闭合的问题，不是固定 Schema 或文件树。可按产品把它们写成 Markdown、状态图、设计稿、Schema、协议定义或组合载体；仅保留适用字段，并通过稳定的规则编号互相引用。不要因载体不同而丢掉规范结果。

| 部分 | 至少回答 | 可复用字段 |
| --- | --- | --- |
| 产品边界 | 谁为谁完成什么结果；纳入、排除和必要依赖是什么 | 范围/版本；参与者与权限；入口与结果；纳入/排除；目标环境；外部提供者及其契约 |
| 行为规则 | 在什么前置条件下，输入怎样经过判定并改变什么；失败、中断、重复和恢复怎样处理 | 规则 ID；适用条件；输入与默认；触发/守卫；结果；副作用；失败状态；重试/恢复；共享规则引用 |
| UI 与体验 | 每个关键任务有哪些视图和状态；操作、反馈、焦点、键盘与响应式变化是什么 | 旅程节点；视图/组件；状态；可见内容与动作；启用条件；文案/反馈；焦点去向；键盘/无障碍；视口约束 |
| 数据与状态 | 概念如何识别，谁有权写入，状态何时提交，数据如何结束生命周期 | 对象/字段；身份；含义/单位；验证/默认；所有者；不变量；状态转换；持久化/删除/保留；迁移/兼容 |
| 接口与配置 | 参与方怎样交换数据；配置从哪里来、何时生效；错误如何表达 | 接口 ID；提供者/调用者；传输/格式；输入/输出；错误与权限；版本/兼容；配置项/来源/优先级/默认/生效时机 |
| 逻辑技术设计 | 哪些职责和系统约束必须成立，才能保证上述产品结果 | 职责/所有者；协作边界；原子性/顺序/并发/幂等；失败传播/恢复；安全边界；运行条件；可检验的性能/可靠性边界 |
| 验收 | 给定什么角色、输入和状态，观察到什么才算满足规则 | 验收 ID；前置状态/数据；操作；可观察结果；错误/权限断言；时间或数值边界；规则 ID |
| 实现自由 | 哪些机制可换，换了仍须保留什么 | 可选项；必须保持的结果/约束；允许变化范围；证明等价的验收 |
| 未决 | 什么尚不能定，影响哪些结果，谁或什么材料能解决 | 问题；已确认部分；缺失输入/证据；影响范围及验收；责任方/来源；下一步；是否阻断最终交付 |

把决定写在唯一权威处：例如跨页面适用的权限规则集中定义为 `R-AUTH`，页面、接口与验收引用它；不要在每页复制出可能漂移的版本。重要未决须指出受影响的实现决定。只影响可替换机制的未知可以留给实现者，但要先给其必须维持的结果。影响产品、体验、安全、外部契约或恢复的重要未知不能标为实现自由，也不能把套件标成最终交付。

事实性质主要用于套件外的调查记录：`已验证事实`注明材料版本、角色、配置和运行条件；`推导设计`写出所满足的已知约束与验证方式；改变目标结果的内容标为`用户批准的改动`；无法闭合的记为`未决`。正式套件写清最终规范，不要求实施者读调查笔记，也不把推断伪装成来源事实。

## 可直接改写的表达

下面四种写法共用“本地 Skill 包预检查”教学范围，并明确假设用户同时要求接入发布流程、且正式包符合完整 Agent Skills/Plugin 标准才允许发布。该预检查产出诊断和退出状态；它本身不是发布门禁，发布流程还要消费结果并执行完整标准校验。数值和行为只在该合成示例内成立，处理真实仓库时须逐项核对来源与用户目标。可按产品改成表格、Schema 或接口定义，但不要省掉会改变实施结果的字段。

**规则**：给规则编号、适用条件、输入判定顺序、结果、失败/副作用和验收。用 `R-REF` 举例：

```text
R-REF  缺失相对引用
适用：可按 UTF-8 读取且被本次遍历选中的 Markdown 文件。
输入：从文件文本识别出的相对目标；同一文件内按目标字符串去重。
判定：跳过规定的外部 URL/绝对目标；其余以该 Markdown 路径的父目录解析，目标不存在则记一个错误。存在的目录也算存在。
结果：每个去重后的缺失目标产生一条含源文件和目标的诊断；该次扫描完成后退出为规则失败。
失败/副作用：若文件无法读取，扫描未完成，不把它计为缺失引用；输入内容不被修改。
验收：两个锚点指向同一缺失文件只报一次；两个不同字面路径即使解析到同处仍分别按规则处理。
```

**状态**：状态名必须对应触发、守卫、写入所有者、可见反馈和恢复；无持久业务状态时也定义一次调用的完成状态。例如：

| 当前状态 | 触发/守卫 | 所有者与变化 | 可观察反馈 | 恢复/验收 |
| --- | --- | --- | --- | --- |
| `scanning` | 发现缺失引用 | 本次检查器追加规则诊断，继续扫描；输入不变 | 最终报告含缺失目标 | 修复后整次重跑，不能删除旧错误继续累计 |
| `scanning` | 读取已发现文件失败 | 本次检查器转 `incomplete`，停止；部分计数无最终效力 | 错误通道说明未完成，无正常结果行 | 修复权限后重跑；发布方不得接受部分输出 |
| `scanning` | 所有文件处理结束 | 本次检查器转 `completed`，汇总诊断 | 统计、诊断和退出状态一致 | 若错误数为零可由发布方继续其自身判断 |

**接口**：即使只是命令，也要给调用方式、提供者/消费者、输入、输出、错误、权限和稳定性。示例：

```text
I-CHECK  skill-precheck <dir> [dir...]
提供者：预检查能力；消费者：维护者与发布流程。
输入：一个或多个目录，按参数顺序分别扫描；相对路径基于调用时工作目录。
成功：stdout 写完整统计与诊断；退出 0 表示扫描完成且规则错误数为 0，警告可存在。
规则失败：仍给完整报告，退出 1；运行失败：stderr 标为未完成，不给正常最终汇总，退出 1。
权限/配置：沿调用进程的读取权限；无提权、无隐式配置文件。
兼容：自动化仅依赖退出码，不解析面向人的诊断文案；若调用者需要稳定机器格式，另定版本化接口。
```

**依赖（仅本例明确要求发布集成及完整合规门禁时）**：选定能力所需的外部提供者或纳入规则要有失败契约，不能只写“由宿主负责”。这里的发布流程和完整标准校验是本例用户要求的消费方及策略，不是所有预检查产品的默认依赖。示例：

| 依赖 | 处理/提供者 | 输入与承诺 | 失败和恢复 | 验收 |
| --- | --- | --- | --- | --- |
| 待检目录 | 目标发布流程提供 | 调用期间可读且内容稳定的目录；提供后启动预检查 | 缺失/不可读视为未完成或输入错误，绝不等同于 0 错误；修复后重跑 | 给不存在、不可读和合法目录，验证发布方仅接受完整成功 |
| 完整标准校验 | 目标发布流程提供，或另行纳入范围 | 在发布前按声明的 Agent Skills/Plugin 标准版本校验正式包 | 标准不通过阻止发布；预检查的 0 不替代此结果 | 构造预检查通过但标准元数据无效的包，发布仍被阻止 |

填写后把每个接口/状态/依赖与规则编号和验收场景互相引用；如果样例比正文多出限制，先修正文。视觉产品还要把这些状态映射到页面反馈、焦点和视觉状态，不能用上述 CLI 示例取代 UI 规范。

本例的发布流程在规则错误、扫描未完成或完整标准校验失败时阻止发布；预检查通过只说明其自身检查已完成且规则错误为零，不证明包符合全部标准，也不等于发布获准。若真实请求只需要生成报告，应移除发布流程和标准校验依赖，并只规定报告内容、完成状态与消费者，不引入门禁语义。

跨页面的共享规则也可以很短，但要覆盖它的全部适用入口和所有者。例如工作区访问规则可定义为：`R-AUTH`：页面只向当前用户列出其有权访问的工作区；切换工作区后清除旧工作区的选择和未完成视图请求；服务端对每次读取、写入和文件下载重新校验工作区成员权限；无权访问的 ID 与不存在的 ID 返回相同外部结果；验收同时覆盖页面切换、直接调用接口和旧请求晚到。报告页、任务查询和下载只引用 `R-AUTH`，不各自改写授权语义。这个例子是规格表达示范，不是对某个仓库的实测结论。

**完整产品的共享规则映射（合成示例）**：假设一个工作区产品有成员、报告和通知三个入口。共享身份与权限只定义一次：`R-IDENTITY` 将请求主体绑定为 `userId + activeWorkspaceId`，切换工作区会丢弃旧视图请求；`R-ROLE` 定义工作区角色能力（admin 可管理成员、生成/下载报告、读通知；member 只读通知；未列动作一律拒绝）；`R-AUTH` 要求服务端每次请求重新授权、所有数据按当前工作区隔离，无权与不存在资源对外一致；`R-JOB` 统一适用后台任务的 `queued → running → succeeded/failed`、服务端唯一状态所有者和终态规则。各能力只引用适用规则，另写自身的结果和验收：

| 能力入口 | 引用的共享规则 | 本能力的验收例 |
| --- | --- | --- |
| 成员管理 | `R-IDENTITY`、`R-ROLE`、`R-AUTH` | admin 添加成员成功；member 直接调用添加接口被拒且成员集合不变；切换工作区后旧列表响应不覆盖新列表。 |
| 用量报告 | `R-IDENTITY`、`R-ROLE`、`R-AUTH`、`R-JOB` | admin 可为当前工作区生成和下载；member 不能直接创建或下载；任务状态遵循 `R-JOB`。 |
| 后台通知 | `R-IDENTITY`、`R-ROLE`、`R-AUTH`、`R-JOB` | member 只读当前工作区通知；另一工作区事件不可见；投递状态遵循 `R-JOB`。 |

这是共享产品规则和能力验收之间的映射，不是被调查产品的行为事实。若角色权限或任务状态在某能力确有差异，应显式定义例外及其验收，不复制一套相互漂移的“公共规则”。

需要把请求、材料、调查、冲突、最终规则和验收连成一条时，读取[UI 与异步任务的合成教学例](example-ui-async.md)。该例中每一条调查结果都标明为合成材料；它展示如何解决版本冲突，并让页面、任务状态、接口、权限与验收保持同一语义，不可移植为其他产品事实。

## 写到什么程度

规则至少写清适用条件、输入、结果、失败与状态变化，并使两个独立实施者不会因空白而作出不同产品决定。必要的界面状态、逻辑职责和数据契约应互相对应。例如“取消”要一致描述控制何时可用、用户反馈、后台状态、已产生数据、重复请求和恢复后的呈现。

区分目标要求、来源声称、实际来源行为和推导设计：文档写了某行为只是来源声称；只有同版本的测试、调用路径或受控运行支持的部分才是已验证事实。规格契约闭合描述的是设计可供实施，不代表实现已开发、集成或验证；规格中生成的报告也不自动构成发布门禁。若另一个流程要把某结果用作门禁，须单独规定消费条件和失败行为。

标出规范必须保持的结果和约束，再列真正可变的语言、框架、存储或内部组织。不能以“实现自由”代替未定义的外部行为、一致性、安全或恢复语义。允许多个结果时写明条件与边界。原仓库技术只有影响兼容或必要约束时才进入规范。调查时使用的操作系统、解释器或库不能自动变成目标产品的支持边界或必装依赖；先核对用户目标环境与可观察兼容要求，缺失的重要平台决定应标为未决。

保持术语和规则单一权威：正文、Schema、样例与验收冲突时明确以何者为准并修正冲突。示例不能暗中新增规则。若声明**精确文本/字节兼容**，对所有实际接受的输入类型说明转成文件名、诊断或报告文本的规则（包括引号、转义、非字符串值），并给能区分两种实现的向量；否则明确允许何种差异。不要一面允许异常类型，一面只为常规字符串定输出。模板和格式检查只能帮助发现缺项；语义完备性要靠场景、交叉检查和脱离原仓库的消费检查。
