# SYSTEM_SPEC/ 输出标准

本文件供撰写与整理正式套件时读取。`SYSTEM_SPEC/` 是概念性根目录；可以是一份主规范加少量契约，也可以按需要拆为多个文件。选载体以能被实施和验证为准，不创建空目录凑齐格式。

## 阅读入口

入口说明目标产品/能力、声明范围、支持环境与版本、明确排除项、文件顺序、术语、规范性权威、外部依赖和验收入口。选择性吸收时列出必要依赖的处理方式。不要把参考仓库路径、内部调查笔记或原实现符号当实施前提。

## 按适用性写全的内容

| 设计面 | 实施者需要知道的内容 |
| --- | --- |
| 产品和参与者 | 用户目标、角色、权限、能力边界、默认值、共享规则和能力组合。 |
| 工作流 | 前置条件、触发、顺序、正常结果、边界、失败、中断、重试、恢复、终态与副作用。 |
| 体验 | 信息架构、入口、导航、每个关键视图和状态、文案/反馈、键盘与焦点、可访问性、响应和视觉约束；无图形 UI 则写实际的人机交互。 |
| 数据与状态 | 概念、身份、字段含义、验证、不变量、所有权、生命周期、持久化/删除、迁移或兼容。 |
| 接口与配置 | 实际对外的 CLI/API/事件/协议/文件格式、输入输出、默认、错误、权限、版本与兼容语义。 |
| 必要逻辑技术设计 | 职责、协作、事务或原子性、并发与幂等、失败传播、安全边界、运行条件、性能与可靠性约束；只写影响结果的约束。 |
| 验收 | 对每条重要规则给出可观察的场景、输入/前置状态、操作、结果和错误断言；适用时给样例或测试向量。 |

不是每类产品都需要同样篇幅。`不适用`须有产品原因；“没看到材料”“工具不可用”是未知或验证限制。对有 UI 的产品，接口列表无法代替交互与视觉状态；对无 UI 的库，不虚构页面。

## 可直接改写的表达

下面四种写法共用“本地 Skill 包预检查”教学范围；数值和行为只在该示例内成立，处理真实仓库时须逐项核对来源与用户目标。可按产品改成表格、Schema 或接口定义，但不要省掉会改变实施结果的字段。

**规则**：给规则编号、适用条件、输入判定顺序、结果、失败/副作用和验收。用 `R-REF` 举例：

```text
R-REF  缺失相对引用
适用：可按 UTF-8 读取且被本次遍历选中的 Markdown 文件。
输入：从文件文本识别出的相对目标；同一文件内按目标字符串去重。
判定：跳过规定的外部 URL/绝对目标；其余以该 Markdown 路径的父目录解析，目标不存在则记一个错误。存在的目录也算存在。
结果：每个去重后的缺失目标产生一条含源文件和目标的诊断；该次扫描完成后退出为规则失败。
失败/副作用：若文件无法读取，扫描未完成，不把它计为缺失引用；输入内容不被修改。
验收：两个锚点指向同一缺失文件只报一次；两个不同字面路径即使解析到同处仍分别按规则处理。
```

**状态**：状态名必须对应触发、守卫、写入所有者、可见反馈和恢复；无持久业务状态时也定义一次调用的完成状态。例如：

| 当前状态 | 触发/守卫 | 所有者与变化 | 可观察反馈 | 恢复/验收 |
| --- | --- | --- | --- | --- |
| `scanning` | 发现缺失引用 | 本次检查器追加规则诊断，继续扫描；输入不变 | 最终报告含缺失目标 | 修复后整次重跑，不能删除旧错误继续累计 |
| `scanning` | 读取已发现文件失败 | 本次检查器转 `incomplete`，停止；部分计数无最终效力 | 错误通道说明未完成，无正常结果行 | 修复权限后重跑；发布方不得接受部分输出 |
| `scanning` | 所有文件处理结束 | 本次检查器转 `completed`，汇总诊断 | 统计、诊断和退出状态一致 | 若错误数为零可由发布方继续其自身判断 |

**接口**：即使只是命令，也要给调用方式、提供者/消费者、输入、输出、错误、权限和稳定性。示例：

```text
I-CHECK  skill-precheck <dir> [dir...]
提供者：预检查能力；消费者：维护者与发布流程。
输入：一个或多个目录，按参数顺序分别扫描；相对路径基于调用时工作目录。
成功：stdout 写完整统计与诊断；退出 0 表示扫描完成且规则错误数为 0，警告可存在。
规则失败：仍给完整报告，退出 1；运行失败：stderr 标为未完成，不给正常最终汇总，退出 1。
权限/配置：沿调用进程的读取权限；无提权、无隐式配置文件。
兼容：自动化仅依赖退出码，不解析面向人的诊断文案；若调用者需要稳定机器格式，另定版本化接口。
```

**依赖**：选定能力所需的外部提供者或纳入规则要有失败契约，不能只写“由宿主负责”。示例：

| 依赖 | 处理/提供者 | 输入与承诺 | 失败和恢复 | 验收 |
| --- | --- | --- | --- | --- |
| 待检目录 | 目标发布流程提供 | 调用期间可读且内容稳定的目录；提供后启动预检查 | 缺失/不可读视为未完成或输入错误，绝不等同于 0 错误；修复后重跑 | 给不存在、不可读和合法目录，验证发布方仅接受完整成功 |
| 完整标准校验 | 目标发布流程提供，或另行纳入范围 | 在发布前按声明的 Agent Skills/Plugin 标准版本校验正式包 | 标准不通过阻止发布；预检查的 0 不替代此结果 | 构造预检查通过但标准元数据无效的包，发布仍被阻止 |

填写后把每个接口/状态/依赖与规则编号和验收场景互相引用；如果样例比正文多出限制，先修正文。视觉产品还要把这些状态映射到页面反馈、焦点和视觉状态，不能用上述 CLI 示例取代 UI 规范。

## 写到什么程度

规则至少写清适用条件、输入、结果、失败与状态变化，并使两个独立实施者不会因空白而作出不同产品决定。必要的界面状态、逻辑职责和数据契约应互相对应。例如“取消”要一致描述控制何时可用、用户反馈、后台状态、已产生数据、重复请求和恢复后的呈现。

标出规范必须保持的结果和约束，再列真正可变的语言、框架、存储或内部组织。不能以“实现自由”代替未定义的外部行为、一致性、安全或恢复语义。允许多个结果时写明条件与边界。原仓库技术只有影响兼容或必要约束时才进入规范。调查时使用的操作系统、解释器或库不能自动变成目标产品的支持边界或必装依赖；先核对用户目标环境与可观察兼容要求，缺失的重要平台决定应标为未决。

保持术语和规则单一权威：正文、Schema、样例与验收冲突时明确以何者为准并修正冲突。示例不能暗中新增规则。模板和格式检查只能帮助发现缺项；语义完备性要靠场景、交叉检查和脱离原仓库的消费检查。
