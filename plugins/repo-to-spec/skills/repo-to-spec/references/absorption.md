# 选择性吸收与依赖闭合

## 何时用、输入与证据

用户只要一项能力、工作流或子系统，并已有自己的产品环境时使用。输入为用户选中的**结果**、目标环境现有能力、已批准的产品改动和参考版本。证据从所选入口、调用方、状态读写、配置、权限、错误/事件和验收测试进入；再查看它调用或假定的共享规则。依赖图以产品责任为节点，不以文件 `import` 为边：一个被调用库可能可替换，一个未直接调用的发布门禁却可能是必要依赖。

## 操作与判断

1. 先写“用户要保留的结果”和明确排除项，再给一个从目标环境入口到该结果的端到端场景。若请求只要结果报告，后续门禁不自动纳入。任何必须由外部提供的输入或后续动作都画在边界上。
2. 对身份/权限、数据及生命周期、配置默认、状态/事件、错误恢复、共享 UI/文案、运行/部署逐一问：拿走来源产品的其他部分，这项能力还能给出同样结果吗？依赖是这个结果必需，还是只为更强的集成方案所需？沿必要项继续追一层，直到遇到自包含规则或目标环境可描述的提供者契约。
3. 每项依赖只选有证据的处理：**纳入**完整规则与验收；**目标环境提供**明确提供者、输入输出、时序、错误、权限及可验收承诺；**改造/排除**会改变原产品结果，取得用户批准并写差异与验收。不能用“由现有系统处理”代替目标环境契约。
4. 若目标环境契约与来源要求冲突，比较可观察后果。等价适配可写成推导设计；改变用户结果、权限或兼容性的方案要用户决定。若需要借用现有执行路径的**一段**（如只做选择、不执行任务），确认目标环境真能在该边界停止且不发生被排除的副作用；接口名称相似不证明可拆。**契约完整而目标尚未实现**时，规格可以完成并明确集成未实现；**提供者能力/语义未核实**时，不宣称集成可用，判断该事实是否影响规格闭合，继续完成不受影响规则。
5. 检查组合边界：所选能力在目标系统何时启动、失败由谁呈现、完成后谁接管、共享数据谁拥有；避免两端都以为对方处理取消、重试或清理。最后用异常场景穿透整条链，而不只验能力内部函数。

正式套件用 `依赖｜必要于哪项请求结果｜提供者/处理方式｜具体契约｜失败与恢复｜验收｜集成核实状态` 表及一条端到端场景表达。若目标环境信息缺失，只能列待核实边界，不能将关键依赖写成“实现自由”。完成条件：删除来源产品其他能力后，所选结果仍可按规格实施、失败并恢复；纳入、外供或获准改变都有明确所有者和验收。规格充分与目标现有代码可立即集成是两个结论。

## 完整示例：把本地预检查接入既有发布流程

用户明确要“发布前只读检查 Skill 包，检查不合格时阻止发布”，目标产品已有发布按钮和作业系统。调查来源预检查的命令/规则/退出状态，以及发布调用方何时调用、是否依赖先编译出的目录。目标环境若只提供一个待检原始目录，而来源检查的是生成目录，必须比较两者内容语义；不能仅因为参数都是路径就判等价。若用户只要检查报告，下文发布决策与完整标准门禁不是报告能力的必要依赖。

| 依赖 | 处理和契约 | 失败与验收 |
| --- | --- | --- |
| 待检包 | 目标发布流程提供稳定、可读的本地目录；若原流程先生成包，应由目标流程提供等价待检产物，或获准改变检查对象。 | 目录缺失/不可读不得被当作零错误；夹具同时覆盖已生成包与目标待检包。 |
| 文件权限 | 由运行预检查的进程身份提供读取与枚举权限；检查器不提权。 | 权限失败是检查未完成，发布不能继续；恢复权限后整次重跑。 |
| 静态规则与报告 | 纳入本能力：输入、遍历、元数据、引用、诊断和退出码。 | 合法、错误、警告、读取失败各有可观察结果。 |
| 发布决策 | 由目标发布流程消费退出状态；非零或未完成必须阻断。警告或零 Skill 是否阻断由目标发布政策决定，不暗改预检查规则。 | 模拟 0、规则失败、运行失败与超时，分别断言发布动作是否发生。 |
| 完整标准验证 | **仅当**用户要求“符合完整 Agent Skills/Plugin 规范才能发布”时，由目标发布流程另行提供或纳入声明范围；只要求“预检查不合格时阻断”并不自动产生此依赖。 | 在要求完整合规的版本中，预检查通过但官方格式无效的夹具仍须在发布前被拒绝。 |

正式范围写明不吸收原产品的蒸馏、Registry、更新或发布实现；不能把它们的内部目录和状态带进下游。若目标发布流程并无“稳定待检目录”，或用户要求完整合规却缺相应验证，输出具体依赖缺口和受影响的发布验收，不能宣告集成可用；可先完成检查报告本身的规格。

**容易做错**：“选中校验脚本，把其他文件删除；发布系统以后自己接。”脚本仍可能依赖生成物形态、权限与退出码解释；遗漏后通过一次正常包测试并不能证明发布门禁成立。另一种错误是为避免依赖而悄悄删掉报错场景或把失败改成警告。
