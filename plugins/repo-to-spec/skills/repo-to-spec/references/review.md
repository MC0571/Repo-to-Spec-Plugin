# 交付审查与缺口处理

在每个能力草案后做局部检查，在整个声明范围形成候选后做一次整体检查。检查结论写明候选版本、范围和实际检查方式。

## 作者自检

1. 用用户请求逐项走查范围和排除项；对选择性吸收检查每项传递依赖的提供者、契约和失败行为。
2. 反向从每个验收场景找到产品规则、交互、状态/数据和必要技术约束；正向从每项重要规则找到至少一个可观察验收点。检查正常、空、错误、中断、重复、并发、恢复、权限和配置等适用条件。凡规则使用“常见”“相关”“按需”等词，给出可判定的边界；解析、筛选和遍历规则至少用正反例锁定识别范围、优先级及计数口径。
3. 检查术语、默认值、状态名、错误和接口在不同文件及示例中一致；指出权威位置。没有依据的产品行为回到调查，必要的推导设计标明理由。
4. 只给正式 `SYSTEM_SPEC/` 时，实施者能否知道要做什么、何时成功/失败、如何反馈、哪些选择可变？查找“参考原项目”“见源码”“按现有逻辑”等回查依赖及内部符号/路径。正式内容不得包含秘密或未经许可的私有材料。
5. 文档/格式/链接检查仅证明结构；不要据此宣布产品完整。

## 独立消费检查

若有未参与撰写且未读参考材料的接收者，只给其声明范围和 `SYSTEM_SPEC/`，请其列出：可直接实施的行为、必须自行决定的产品/体验/技术问题、矛盾、隐含外部依赖及无法据此写出的验收。记录接收者身份/隔离方式、提出的问题、修订与复查。若作者自己模拟，只能称作者自检。独立实现或真实用户验收是更强证据，但不是每次任务默认要求。

## 交付状态

- **最终套件**：声明范围内无已知影响独立实施的重要未知；必要依赖有契约；作者检查完成，独立消费检查的实际状态如实记录。
- **草案/阻塞**：指出缺的具体材料、运行条件、权限或用户决定、已做调查、影响的设计与可继续的部分；不要把阻塞隐藏在“实现自由”或空白模板里。
- **发现问题后**：先修正规范或方法中产生问题的原因，再重查受影响内容；不能只润色一份样例。一次样例成功只证明该范围与环境的实际覆盖。
