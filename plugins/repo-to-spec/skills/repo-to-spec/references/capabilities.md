# 能力发现与边界划分

## 何时用、拿什么开始

用户说“整个产品”“某模块”但没有列出用户结果，或源码目录看似天然分区时使用。输入是请求原文、产品/用户说明、可运行入口、目标版本和已有产品上下文。先确认所见材料与请求版本相同；README 中的愿景、未发布计划和当前行为分开记录。

证据从用户可到达的入口开始：导航、命令帮助、API、示例、用户文档、验收/行为测试；再沿调用者、状态写入和输出追到实现。目录只帮助定位。搜索同一动词的反向调用和共享配置，查看该能力是否被另一个流程复用。

## 操作与判断

1. 把请求写成一句用户结果：**谁在什么条件下完成什么，得到什么可见结果**。列出最小正例、一个边界或失败例和使用入口；仍不把它们当已证实行为。
2. 从入口追踪到最终结果，标记每个参与者、触发、输入、状态和输出。再从结果反向追踪：还须由谁提供身份、数据、默认值或发布/通知动作？用测试、文档或受控运行交叉核对至少一个关键转换。
3. 按可观察目的划能力边界：一起改变同一用户结果、共享不可分割的状态或失败语义的规则放在同一能力；只提供独立输入契约的部分可以成为依赖。一个源码模块服务多个用户结果时拆开描述；多个模块协作完成一个结果时合并描述。
4. 对每项邻接行为做选择：**纳入**（缺它就无法得到请求结果）；**外部依赖**（目标环境可提供可验收契约）；**排除**（拿掉后请求结果仍成立）；**待用户决定**（改变产品结果或范围）。共享规则只在一个权威位置定义，各能力引用其规则名和适用条件。
5. 用“从用户入口能否走到声明结果”反测范围，再查是否误把内部构建、维护工具或实现目录写成产品能力。全产品请求还须从所有公开入口重复此过程；单一能力请求只扩到必要依赖。

输出可先用短表：`能力/用户结果｜入口与参与者｜包含｜排除｜共享规则/提供者｜证据性质｜待核对`。正式套件把已定范围写成产品语义和验收边界，源码位置留在套件外。若入口不明，先用使用说明和测试寻找；若两个入口结果矛盾，核对版本、配置和权限，仍不明就标未决，不能凭目录名选一个。完成条件是每个声明结果都能从入口、规则、状态和输出走通；边缘能力有明确处理，且下游不会自行决定是否包含某项必要行为。

## 完整示例：只吸收本地 Skill 包预检查

以下是方法示范；实际任务须对指定提交重验。请求是“用户在发布前只读检查本地 Skill 包”，目标产品已有发布流程。入口证据为预检查命令及发布前调用、规则证据为读取 Markdown/frontmatter/引用的测试和受控错误样本；运行结果只支持所用版本与夹具。

| 判断 | 调查结果与决定 |
| --- | --- |
| 用户结果 | 维护者给定目录，得到可定位的诊断、统计与是否可继续发布的退出状态；输入内容不被改写。 |
| 纳入 | 参数与遍历、元数据和引用识别、错误/警告、读取失败、报告与退出码。只写“检查”会让实现者自行发明结果语义。 |
| 排除 | 内容蒸馏、编译、Registry、更新和真正的发布；它们不参与产生检查报告。 |
| 共享边界 | 发布流程提供待检目录并消费退出码；完整格式合规验证若由发布流程承担，须明说其独立责任，不能把预检查通过等同于可发布。 |
| 需补查 | 若命令测试只展示正常包，继续造缺引用、坏编码、重复根和目录权限夹具；运行不了权限夹具时其行为仍是待核对或有依据的推导，不写“实测”。 |

正式范围可写：“本能力接收一个或多个本地目录，仅读取并产生诊断、统计和退出状态；不修改输入、不执行包内代码、不触发发布。目标发布流程提供目录并依据退出状态决定后续动作。”验收分别给合法包、损坏元数据、不可读取文件和发布流程拒绝非零退出。这样声明的是完整用户结果，而不是原脚本所在目录。

**容易做错**：“`scripts/validate_skill_pack.py` 是一个模块，所以只复制它的正则和打印函数；发布目录、退出码与权限由别处处理。”这会漏掉真正的输入与发布契约，也把源码边界误作产品边界。若用户明确要连同发布一起重建，以上排除必须重新判定。
