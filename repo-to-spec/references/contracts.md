# 数据、接口与必要技术约束

## 适用、材料与证据入口

当产品结果跨进程、持久化数据、配置、权限或并发边界，或规格只写“保存/调用接口”时使用。输入为能力范围、行为状态、支持环境、示例数据、公开 API/CLI/文件、Schema/迁移、配置样例、调用方和测试。先看外部消费者实际使用的字段/命令，再看生产者、验证与存储；单个内部类型定义不能独自证明公开契约。敏感数据只记录语义，样例脱敏。

## 操作与判断

1. 建立概念表：每个业务对象的身份、字段含义、类型/单位/范围、缺失与显式空值、必填/默认、所有者、创建/更新/删除时机、提交点与不变量；用读写双方和正反样本核对。区分公开格式、内部表示和临时计算值。
2. 对每次跨边界交互列提供者、调用者、触发/时序、完整输入、成功输出、错误类别、权限、版本/兼容和重试语义。CLI 要追参数解析、配置文件/环境/命令参数的默认与覆盖顺序，以及 stdout/stderr/退出码是否与内容结果一致；API 要看鉴权、分页/排序；事件要看投递、确认、重复与顺序；文件要看编码、路径与原子交付。发现字段在客户端和服务端意义不同时，先核对版本与兼容层。
3. 用状态不变量推导必要技术约束：职责如何协作，谁拥有并可写状态，何时算提交，部分成功允许到什么程度，重复/并发请求如何决议，资源由谁释放，失败后如何恢复。只规定能影响可观察结果或安全的原子性、顺序、资源、性能边界；内部模块和数据库产品不是默认约束。来源未逐字写出所有权时，若已确认结果足以推导，给有理由的目标设计，不把必要设计留给下游。
4. 排查配置和安全：默认/优先级/生效时机，角色和数据可见范围，秘密如何输入、日志哪些信息不得出现。若来源依赖外部身份或队列，明确目标环境提供的契约与失败行为。
5. 若报告、评分或缓存会控制后续动作，列出其**全部有效性输入**：被测内容、规则/用例版本、配置/阈值、竞争环境、执行器版本与权限等。消费者据哪些条件判断旧结果仍适用？一项语义输入变化就不能只靠旧报告的文件名或单一内容摘要放行。保留集等不能向调优方泄露的信息还须说明谁可见逐例结果、何时可见、曝光后怎样管理。
6. 对每个接口用一组正反例核对：合法输入/结果、非法输入/错误、重复或冲突、权限不足；再用实际消费者检查规格是否足够。对批量/多目标请求，从单项结果追到聚合决定，明确部分失败是否阻止整体成功。仅有源码类型却无可观察语义时继续读测试、文档、调用方或受控运行。

正式表达可用对象字段表、状态转换、接口表和不变量；复杂机器可读格式仅在下游会实际使用时提供。来源无法确定的兼容期限、数据保留或性能数值不可凭经验填；注明影响、可继续部分及需谁决定。完成条件：另一团队可定义自己的内部存储和服务划分，却仍能得到相同的数据含义、权限、外部交换、错误及一致性结果，并能逐项验收。

## 完整示例：名单导入契约（教学假设）

假设仓库提供上传端点、导入任务表、前端状态测试和部分成功样例；这是教学材料，不代表任何已调查仓库。调查先核对客户端是否用 `requestId` 重试、服务端是否真的按它去重、任务表的失败行何时可下载，再决定下列值能否进入正式规格。

| 对象/字段 | 意义与不变量 |
| --- | --- |
| ImportJob.id | 服务端生成、全局唯一；同一 `requestId` 在同一租户内映射到同一任务。 |
| ImportJob.state | `accepted → processing → completed/partial/failed`；`completed/partial` 在全量解析并一次提交合法行后成立；本示例的意外运行故障进入 `failed`，尚未提交的合法行不落库。终态不可返回处理中。 |
| acceptedCount/rejectedCount | 只计已完成解析的行；仅 `completed/partial` 表示全量解析结束，此时两者之和等于非空输入行数。`processing/failed` 的计数若显示，仅代表已处理进度，不作最终导入承诺。 |
| errorFile | `partial` 时可获取行错误明细；`failed` 若发生于解析中途，须说明运行失败，不能提供冒称完整的行错误文件。只由同租户管理员读取；过期策略若材料未说明不得猜定。 |

接口表达示例：`POST /imports` 接受 CSV 文件和 `requestId`，成功返回 `jobId,state=accepted`；同租户同 key 同内容重发返回原 `jobId`，同 key 不同内容返回冲突；无管理员权限返回拒绝且不建任务。`GET /imports/{jobId}` 仅同租户管理员可见，返回状态与当前/最终计数；任务不存在与无权访问的错误是否区分须按目标安全边界决定。服务端在接受请求前验证文件类型和可读性；行级验证在任务内发生，部分成功允许保留合法行。若材料没有证明同 key 行为，以上幂等规则只能是待核对方案，不能冒充恢复事实。

验收：两次同 key 同内容提交得到同一任务；同 key 不同内容冲突且任务数不变；无权用户无法读取任务与错误文件；部分成功的计数和错误文件行数一致；模拟解析中途运行失败时状态为 `failed`、零行提交，部分计数不冒充全量结果且不能下载“完整行错误”；任务终态后页面结果与查询接口一致。实现可以选 SQL、对象存储或任务队列，但必须满足这些可见不变量和授权边界。

**容易做错**：“有 `import_jobs` 表，字段按 ORM 模型照搬；REST 接口返回 200 或 500；使用原仓库的队列和数据库。”这没有定义租户可见性、重复提交、部分成功、数据生命周期或错误语义，且把偶然存储选择当作产品要求。
