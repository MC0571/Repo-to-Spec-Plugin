# 实现解耦：从原机制恢复必要约束

## 适用、输入和证据

看到原仓库的语言、框架、数据库、解析库、目录、算法、平台或调查工具，准备把它写成“必须”时使用；也用于检查已生成规格是否把运行环境误判为产品依赖。输入是目标范围与支持环境、可观察行为、外部兼容对象、部署/运维要求、原实现与锁文件、测试、实际调用者和用户批准的改变。入口先看用户怎样安装/调用、交互结果和外部格式，再看该技术选择承担了什么责任。源码 `import` 只证明原实现用了库，不证明新实现必须使用它。

## 五步判断

1. 把候选技术要求改写成它声称保护的结果：“需要 X，因为没有 X 就无法满足 Y”。明确 Y 是外部兼容、用户体验、安全、性能、部署条件，还是作者调查方便。写不出 Y 时，X 不进入规范。
2. 找至少一种不同机制尝试满足同一 Y，并检查现有测试/协议能否区分两种实现。若两者对所有要求等价，规范写 Y 和验收，X 放实现自由；若差异会被调用方、用户或运维看见，写清差异与适用条件。
3. 分清四类：**外部契约**（字节格式、命令、协议、兼容平台，需定值）；**必要系统约束**（权限、隔离、顺序、资源上限等，需给可检验边界）；**原实现机制**（库、框架、模块、存储，通常可替代）；**调查条件**（作者机器上的 OS/解释器/安装包，绝非自动目标要求）。同一项可能跨类，例如 YAML 解析库是机制，但其安全加载和类型语义是结果约束。
4. 目标平台不明确时，先查用户上下文、公开安装说明和实际消费者；若选择平台会改变交付产品，列待决问题和受影响验收，不能用调查机器的平台填空。平台已定但来源不支持时，标为迁移设计与待验证，不伪称原产品已支持。
5. 在正式规格成对写出“**必须保持的结果/约束**”与“**可替换机制**”，给能发现偏差的验收向量。若选型本身受外部插件 API、二进制兼容或许可条件约束，写出权威依据、版本和不能替代的部分；未核实则保持未决。

缺材料时，优先补查对外消费者、格式样本、异常测试和部署说明；若无法证明某机制必要，先不要把它定为必装。若无法确定结果语义，则不能仅靠开放语言/框架选择宣布完成。完成条件：陌生团队知道哪些结果不可变、哪些机制可选，且至少一个替代实现思路不会改变声明行为；必要的兼容/运行限制有证据或明确的产品决定。

## 完整示例：预检查的 Python/PyYAML 误判

已安装插件的原始样例调查使用 Python 3.12 与 PyYAML 6.0.3，原输出曾把它们写成目标运行前提。复核时先问它们保护什么：真正的结果是 UTF-8 文件遍历、特定 YAML 安全加载语义、诊断顺序和退出状态。用其他语言与等价安全解析器也能满足这些观察点；没有已知外部调用方要求 Python API。因此正式表达改为：

| 层次 | 规格写法 |
| --- | --- |
| 必须 | 给定相同可读输入，在声明环境内按规定识别 YAML 类型/错误并产生同样的诊断、计数和退出状态；不得执行被检包的代码。 |
| 可替换 | 实现语言、YAML 库、内部模块和打包方式；选择外部库的实现自行提供它，缺库时不得假装检查通过。 |
| 支持环境 | 样例最终把本地 POSIX 与 UTF-8 终端写成其选择的范围；这是样例范围说明，不是从 Python 调查环境推导出的普遍插件要求。若实际用户要求 Windows，须继续调查/设计该平台，不得沿用此限制。 |
| 验收 | 用布尔/数值/多行 YAML、未知 tag、坏编码、重复根和权限失败夹具比较结果；在非 Python 实现上也应成立。 |

该案例的保存版本是**原始生成后经评审修订**，不能将修订倒写成原始 Agent 已正确判断。原始记录、修订理由和重验状态应留在验证记录中，正式套件只呈现确定的目标契约。

**容易做错**：“源码导入 PyYAML，所以用户必须安装 Python 和 PyYAML；我在 macOS 上调查，所以只支持 macOS。”这把原机制和调查条件提升为产品约束，既缩小目标平台又锁死可替代实现。反过来，写“任何解析器都可以”也错：若它把 YAML `false` 变成非空字符串，规则结果已经改变。
