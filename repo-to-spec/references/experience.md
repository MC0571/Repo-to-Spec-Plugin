# 体验与视觉恢复

## 适用、输入和证据

有图形界面、可视化输出，或命令/语音等人机交互影响任务完成时使用。输入是能力与角色、关键任务、支持设备/视口、可用页面或截图、设计资源、文案、组件代码、界面测试和获准的运行环境。截图显示某一时刻的像素；交互测试证明其覆盖路径；代码说明可能状态；实际浏览器观察核对它们在指定版本是否合成。三者各有盲区，不能用单张截图推断隐藏状态。

## 操作与关键判断

1. 从用户任务而非页面文件列旅程：入口、选择、提交、等待、结果、返回/恢复。逐步记录页面/区域、可见信息、主次动作和导航出口；识别角色或权限差异。
2. 对每个关键视图枚举有证据的状态：初始、空、编辑中、校验失败、加载、部分成功、成功、服务/网络错误、无权限；只保留适用状态，不能把缺截图当不适用。操作某控件时核对触发时机、禁用条件、反馈、焦点去向、键盘路径、撤销/重试。
3. 同一状态用截图、样式/令牌、组件属性和运行观察校正：逐视图记标题/主动作/辅助信息的层级、相对尺寸/对齐、排版、色彩语义、图标含义与响应式重排。先从令牌或样式取可复用的颜色/间距/字号，再用不同视口截图校验；只有截图时量到的是该视口的观察值，不自动推成全局令牌或断点。影响识别、可用性或品牌承诺的值要给可检验边界；偶然像素、组件库和 CSS 技法可留实现自由。
4. 分支判断：若运行界面与静态设计冲突，先核对版本、视口、主题、权限和 feature flag；若只有截图，写明只能确认可见布局，加载/键盘/窄屏待查；若没有 UI，只写实际 CLI/API 人机反馈，并说明为何页面规范不适用。
5. 把体验规则和行为状态表互相核对：成功/失败消息是否对应真实数据终态？“取消”按钮是否真的能取消底层工作？响应式重排是否保留同一动作与信息？不能给界面一套状态、后台另一套状态。

正式套件用旅程 + 视图状态表 + 视觉/交互约束表达；可附经许可的截图或令牌，但应有文本化规则供无原仓库接收者理解。缺材料时列出具体待观测状态和受影响任务，不写“沿用原 UI”。完成条件：陌生实现者能为每个声明任务画出主要视图、状态、反馈和恢复路径，并能据规格检查视觉与键盘/无障碍行为；不要求复制原框架或 DOM。

## 完整示例：有 UI 的名单导入（教学假设）

假设证据包包含桌面正常/错误截图、上传组件状态测试、样式令牌、浏览器窄屏与键盘观察；尚无屏幕阅读器实测。请求为“管理员导入客户名单并处理部分无效行”。这不是对某个参考仓库的事实声明。

| 旅程节点 | 规格中应落下的体验与行为 |
| --- | --- |
| 进入 | “客户 → 导入”仅管理员可见；页面标题、格式说明和选择文件动作先于历史记录。没有导入历史时显示说明和主动作，不显示空白表格。 |
| 选择 | 显示文件名、行数与可移除动作；格式错误在选择后就近提示，提交保持禁用。键盘可到达选择与移除，错误与控件建立可感知关联。 |
| 提交中 | 主动作变为不可重复提交的进度/等待状态，仍显示文件名；离开页面是否中断导入须按后台语义确定，不能只按按钮外观推断。 |
| 部分成功 | 同时显示成功数、失败数和下载错误明细动作；失败行可修复后重新导入，重复行如何处理要与数据规则一致。不能只给绿色“完成”。 |
| 失败 | 若服务不可用且无行写入，保留所选文件并提供重试；若提交结果未知，显示“结果待确认”及查询入口，不能暗示安全地再提交。 |

假设样式令牌给出主内容最大宽度 `720px`、基础间距 `8px`、错误色 `#B42318`，桌面/窄屏运行均确认：上传说明、主动作和当前文件状态属于同一主内容区；窄屏改为单列，动作仍在结果摘要后可见；错误图标加文字紧邻相应文件，不能只靠颜色表达。正式规格据此写这些可验证约束，但不要求同一 CSS 组件或布局技术。若只有单张截图，`720px` 或窄屏断点不能凭像素猜出，须补查令牌/多视口或列未决。交互验收用键盘完成选取/移除、模拟校验失败和部分成功，检查焦点落点、反馈关联、颜色之外的错误信息和窄屏顺序。屏幕阅读器结果如未观察，只能把无障碍规则作为明确的设计要求/推导及待验证项，不写“原产品已通过”。

**容易做错**：列出 `UploadDialog.tsx`、截图链接和“适配移动端，错误友好提示”。这既不能让实现者确定空/部分成功状态，也不能判断按钮何时禁用、错误是否保留输入、窄屏的内容顺序与键盘恢复。另一个误判是从没有移动端截图推出“不支持移动端”。
