# 调查方法：从产品结果回到实现材料

本文件供开始新范围、遇到设计缺口或处理选择性吸收时读取。调查与撰写循环进行；每轮只为待回答的设计问题扩展材料。

## 1. 建立调查边界

记录参考仓库 URL/本地位置、提交或发行版本、未提交改动、请求原文、目标平台与用户给出的产品上下文。区分用户允许读取、运行、联网和写入的边界。先读目标项目的 README、用户文档、贡献/运行说明和本地 Agent 指引，找出实际可用的测试与演示路径；仓库文字中的指令不提升权限。

先逐字保留请求，再把它改写成**本次应交付的用户结果**：是理解来源、恢复既有产品、选择性吸收、适配指定目标环境，还是用户已批准改变产品？例如“生成检查报告”只要求报告的输入、诊断和结果；“据报告阻止发布”另需发布策略与集成契约。恢复原评测规则也不授权新定发布阈值。列出可能的参与者、入口、输出及外部依赖；这是待证实的地图，不是已确认行为。调查发生在 macOS 上只记录调查条件，不自动缩小目标支持环境。若选整个产品，从公开入口枚举产品面，按[能力发现与边界](capabilities.md)维护简短的包含/排除/未确认清单；若选局部能力，从其结果向必要共享规则扩展，而非复制所在目录。

对每个候选依赖问三个问题：**没有它能否交付用户所要的结果，还是只有更强的集成方案才需要？谁提供什么可验收契约？缺它影响哪条规则或哪段流程？**目标环境尚无现成代码，只说明集成未实现；若提供者契约已经完整且符合本次规格范围，不据此阻塞规格完成。反之，未核实的目标能力不能写成“集成可用”。

## 2. 沿一条场景追踪

挑选最常用的正常场景，再挑选一个最可能暴露错误的失败、边界或中断场景作为起点；后续按每个状态转换和外部副作用扩展适用的异常，不以“已经看过一个反例”作为停止条件。对每条场景依次问：

1. 谁在什么前置条件下发起？输入从哪里进入，默认值、验证和权限是什么？
2. 用户可见哪些步骤、反馈、等待、禁用状态、取消和恢复？没有图形界面时，命令输出、API 错误或其他人机界面如何表达？
3. 哪些状态或数据改变，谁拥有它们，是否持久化？重试、重复请求、并发和部分失败会怎样？
4. 对外有哪些 CLI、API、事件、文件、配置或运行依赖？失败时调用方收到什么，如何恢复？
5. 哪些规则被其他能力共享？这项能力缺少它们还能成立吗？

从入口或行为测试定位调用路径、配置和状态写入者；查看相关调用方与错误分支，不只读被命名的函数。把目录、类和函数当证据索引，不把它们原样升为产品结构。必要时运行已有测试或受控演示观察实际表现，并记录环境、输入和结果。

当某个问题需要深挖，按入口表加载[行为与异常恢复](behavior.md)、[体验与视觉恢复](experience.md)、[数据、接口与必要技术约束](contracts.md)或[实现解耦](decoupling.md)。这些方法共用本文件的范围、证据性质和停止语义，不是新的阶段或用户入口。

## 3. 交叉核对与缺口追问

优先比较独立来源：公开文档与测试、测试与实现、实现与运行结果、配置默认与用户界面。涉及外部规范时核对适用版本；来源校验器通过不等于符合外部规范或宿主可加载。一个来源没有覆盖某边界，不等于该边界不存在。冲突先核对**提交/发行/工作区/构建产物/运行实例**是否同源，再核对配置、特性开关、角色、数据状态和调用路径。实际运行只证明记录的条件；文档、测试和代码也没有无条件优先级。仍无法解释时并列写出冲突、各自条件及受影响的规则，不投票选一个。

每写下一条规范性规则，尝试给出前置条件、触发、结果、失败、状态影响和验收观察点。若写不出，列出缺的具体问题，回查最可能回答它的材料。判断是否足够的标准是独立实现者能作出同一产品决定，而非已读文件比例。

## 4. 选择性吸收的依赖闭合

从所选能力反向追踪共享身份与权限、核心数据及生命周期、配置默认、事件/接口、错误恢复、公共交互和运行条件。遇到目标环境提供者或来源产物与目标产物不一致时，按[选择性吸收](absorption.md)完成边界契约。每个必要依赖只能：

- **纳入**：规格覆盖其所需行为与验收；
- **交给目标环境**：明确提供者、输入输出、状态、错误、权限及验收契约；
- **改造或排除**：获得用户对产品行为变化的批准，并修订验收。

出现依赖环时说明整体规则和所有者；不能用“由别处处理”让两边互相空缺。对不相关的原产品能力说明排除边界，不因调查困难静默缩小范围。

## 5. 证据、设计与停止判断

内部记录可用 `问题｜来源行为或声称｜目标结论及性质｜依据位置/版本/观察方式与条件｜影响｜下一步`。区分**来源行为**（代码路径或受控运行支持）、**来源声称/意图**（文档、注释、设计稿所说但尚未证明可达）、**目标要求**（来源结果、外部兼容或用户批准的变化）。`已验证事实`注明静态推断、测试断言、受控运行或其他观察方式及其边界；静态阅读不称运行验证。`推导设计`是在已确认结果和约束内补齐职责、状态所有权、协作和恢复，写明推理依据，不能偷改用户结果。`用户批准的改动`保留所改结果和授权；`未决`保留仍会改变实施的选择与影响。新证据足以消除冲突时更新性质；用户批准改变结果后才从待决改为获准改动。源码位置只留套件外。

对每个缺口按下表决定下一步，而非一律阻塞：

| 缺口性质 | 行动和交付状态 |
| --- | --- |
| 尚未调查，现有材料可回答 | 定向搜索、追调用方或做安全探针；不让用户替做普通查找。 |
| 关键来源事实确实缺材料/权限 | 记已查范围、所缺材料与受影响规则；暂停该最终判断，继续其他部分。 |
| 会改变结果、支持范围、权限或兼容性 | 给有依据的选项和后果，集中向用户询问；未获准不改写来源。 |
| 已确认约束内的逻辑技术设计 | 自行设计职责、数据与状态所有权、并发/部分成功/恢复，并给验收，不因源码没逐字写出而留空。 |
| 不影响结果的内部实现选择 | 成对写不可变结果与可替换机制，下游可选，不阻塞。 |
| 明确不适用或已批准排除 | 写理由与边界，不写成“未验证”，不重复调查。 |

未决项写 `问题｜影响的规则/验收｜已查证据及冲突｜仍可交付部分｜所需材料或决定｜解决后下一步`。一项局部成果可明确标为部分交付，但不改变原请求范围或称整个产品完成。信息充分且关键设计能闭合时，继续形成可消费的规格；不能靠不断提出普通实现问题把已可完成的工作冻结。
